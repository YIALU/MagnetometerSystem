# 发布流程

发布版本配置的唯一入口是 [`Directory.Build.props`](../Directory.Build.props) 的 `<Version>`。正式产物必须来自干净工作区，当前提交的 **annotated tag `vX.Y.Z`** 必须与该配置一致；构建产物、程序集版本、附件名称和 Release 标签应指向同一版本、同一提交。本文以 **0.5.1 / v0.5.1** 为例。

当前开发版支持 GitHub / Gitee 双平台更新，默认比较两边正式版本，也可指定平台。**已发布的 V0.5.0 客户端仍只查询 Gitee**，仅发布 GitHub 不能让这些旧客户端发现更新。维护者已授权：每次改动经 PR 审查合并后同步 Gitee 主分支；软件代码交付同时在两平台推送标签并创建 Release。

提交与审查规则见 [CONTRIBUTING.md](../CONTRIBUTING.md)。发布 Release 不等于合并 PR：PR 最新提交的审查与 CI 通过后直接合并，再在合并提交上打标签发布，并在 Release 说明中记录 PR 和提交 SHA；不直接推送主分支，不用自动合并跳过审查。

## 前置条件

| 项目 | 要求 | 检查方式 |
| --- | --- | --- |
| 环境 | Windows、.NET 8 SDK | `dotnet --info` |
| Inno Setup | 推荐 7；安装包需要兼容编译器及简体中文语言文件 | `ISCC.exe /?` 并检查 `Languages/ChineseSimplified.isl` |
| Git | 可读写本仓库及目标远程 | `git remote -v` |
| GitHub CLI | 使用下方 CLI 发布示例时需要已登录 | `gh auth status` |

脚本至少需要 Inno Setup 6.4，并引用 `compiler:Languages\ChineseSimplified.isl`；部分 6.x 安装包不带该文件，不能只看版本号判断可用。本次使用带简体中文语言文件的 Inno Setup 7。仓库不内置该语言文件；不要把新语言文件配给旧编译器，否则可能出现 `unknown message name`。缺少编译器时可按本机管理方式安装，例如 `winget install --id JRSoftware.InnoSetup -e`，随后检查实际编译器与语言文件。

本仓库远程名称：`origin` 指向 `https://github.com/YIALU/MagnetometerSystem.git`，`gitee` 指向 Gitee。每次发布先核对 `git remote -v`，不要套用 `origin main` 等旧示例。

## 第 1 步：准备版本与说明

版本号使用严格三段 `主.次.补丁`。修复通常提升补丁号，功能更新通常提升次版本号；不使用 `v1.2`、`v1.2.3.4` 或 `v1.2.3-beta` 作为本流程的正式版本标签。

更新 `Directory.Build.props`：

```xml
<Version>0.5.1</Version>
```

同步更新 [变更日志](变更日志.md)、README 下载链接及必要的验收说明。发布说明要区分自动测试、UI 检查和真实设备验收，明确尚未验证的范围，不把 TCP/mock 测试写成实体串口验证。

只暂存本次实际修改的文件，逐项检查后提交。以下是版本准备所涉及路径的示例，未修改的文件无需暂存：

```powershell
git status --short
git diff
git add -- Directory.Build.props README.md README.en.md docs/变更日志.md docs/发布流程.md
git diff --cached
git commit -m "chore: prepare v0.5.1 release"
# 确认当前是功能分支，再推送到 GitHub PR。
git branch --show-current
git push origin HEAD
```

不要使用 `git add -A` 或 `git add .` 混入无关代码、数据库、个人配置或产物。

## 第 2 步：验证并审查最终提交

在 Windows 下按当前提交运行构建与测试；串行执行可避免共享构建输出竞争：

```powershell
dotnet restore MagnetometerSystem.sln
dotnet build MagnetometerSystem.sln -c Debug --no-restore -m:1
dotnet test MagnetometerSystem.sln -c Debug --no-build --no-restore -m:1
```

记录实际提交 SHA、通过/失败/跳过数量及跳过原因。其他验收见 [testing-and-acceptance.md](testing-and-acceptance.md)。

确认 **最新 PR HEAD** 的 `Windows build and tests` 成功、Codex 审查完成且有效问题已处理。新增提交、解决冲突或更新基础分支后，要重新核对最新提交，旧审查不能覆盖新提交。审查未运行、超时或额度不足不视为通过。

可以选择已审查 PR 的提交作为发布来源，无需为发布而擅自合并 PR。记录它的完整 SHA 和 PR 链接；若发布来源改为维护者合并后的提交，同样重新核对该提交的验证状态。

## 第 3 步：在已验证提交上创建标签

打包前 `git status --porcelain` 必须没有输出。保留并妥善处理未提交工作，必要时使用干净 worktree；不要用清理或强制重置覆盖其他人的修改。

确认当前 HEAD 就是已验证的发布来源后创建 annotated tag：

```powershell
git status --porcelain
git rev-parse HEAD
git tag -a v0.5.1 -m "Release v0.5.1"
git cat-file -t v0.5.1
git rev-parse 'v0.5.1^{commit}'
git describe --tags --exact-match HEAD
```

`git cat-file -t` 应输出 `tag`；标签解引用出的提交应与已审查 HEAD 一致，精确标签应为 `v0.5.1`。若标签已经存在，先检查其对象与提交，不覆盖或强制移动发布标签。

标签创建后不再修改发布源码。若仍需代码修复，回到提交、测试和审查步骤，不用 `-AllowDirty`、`-SkipVersionCheck` 或版本覆盖参数绕过正式发布检查。

## 第 4 步：从干净工作区打包

```powershell
.\build.ps1 -Mode All
```

脚本会用 `git describe --tags --exact-match HEAD` 取版本，与 `Directory.Build.props` 交叉检查，并拒绝未提交或未跟踪的工作区变更。上述人工步骤另外确认 annotated tag 与审查来源；脚本检查不能替代代码审查。

产物位于 `artifacts/v0.5.1/`：

| 文件 | 说明 |
| --- | --- |
| `MagnetometerSystem-v0.5.1-portable-win-x64.zip` | Windows x64 便携版，单文件应用及附带文件 |
| `MagnetometerSystem-v0.5.1-setup.exe` | Windows x64 安装版，Inno Setup 安装包 |
| `SHA256SUMS.txt` | 两个包的 SHA256 校验清单 |

其他模式：`-Mode Portable` 仅生成便携版，不需要 Inno Setup；`-Mode Installer` 仅生成安装版。完整发行使用 `-Mode All`，并核对两个包与同一次构建的校验清单。`artifacts/` 已在 `.gitignore` 中，不提交到源码。

更新器按**当前 Release 版本的完整附件文件名**选择包：便携版明确匹配 `win-x64`；安装版的固定名称是 `-setup.exe`，没有额外架构后缀。不是按任意 `-setup.exe` 或 `-portable-*.zip` 后缀宽松匹配，不能改名，也不能把旧版本或其他架构的包混作当前版本。

### 两种分发形态

| 项目 | 便携版 | 安装版 |
| --- | --- | --- |
| 发布方式 | ZIP 中的单文件应用 | 展开目录加安装器 |
| 安装位置 | 用户自选 | `%LOCALAPPDATA%\Programs\MagnetometerSystem` |
| 需要管理员权限 | 否 | 否，`PrivilegesRequired=lowest` |
| 识别标记 | 程序目录有 `portable.marker` | 无此文件 |
| 更新行为 | 下载后打开目录，用户手动解压覆盖 | 保存完成后启动安装器，安装后重启 |

`AppVersion.PackageKind` 按 `portable.marker` 区分分发形态，决定下载资源和应用更新方式。

## 第 5 步：发布 GitHub Release

确认 GitHub 已有被审查的源提交，再仅推送本次标签：

```powershell
git push origin refs/tags/v0.5.1
```

在 [GitHub Releases](https://github.com/YIALU/MagnetometerSystem/releases) 创建发行版，选择已存在的 `v0.5.1`，标题为 `v0.5.1`。说明取自变更日志，并补充来源 PR、完整提交 SHA、最终验证结果和硬件验收边界。上传上表三个文件，不能只上传安装器而遗漏校验清单。

### 面向用户的更新说明

两平台 Release 使用相同的用户摘要，用简短中文写清使用变化、修复问题和必要操作。摘要使用纯文本，放在下列标记之间，应用更新窗口优先展示这部分；PR、提交、CI、包名和验证边界放在标记之外，用户可展开完整说明查看。未提供有效摘要的旧 Release 保留完整说明入口，不猜测其更新内容。

```text
<!-- user-notes:start -->
关闭软件时会显示保存进度，保存失败时给出处理方法。
发现新版本只会提示，是否下载和安装由您决定。
简化更新与反馈页面的说明，反馈内容公开范围保持清晰。
<!-- user-notes:end -->

## 验证与来源
填写实际 PR、提交、构建和测试结果，以及未验证的设备场景。
```

发布前分别检查 GitHub / Gitee 的摘要、完整说明、版本与下载目标，用户摘要不能声称尚未验证的功能已可靠实现。

也可用 CLI。先把确定的发布说明保存到 `artifacts/v0.5.1/release-notes.md`（不作为附件上传），然后运行：

```powershell
gh release create v0.5.1 --repo YIALU/MagnetometerSystem --verify-tag --title v0.5.1 --notes-file artifacts/v0.5.1/release-notes.md artifacts/v0.5.1/MagnetometerSystem-v0.5.1-portable-win-x64.zip artifacts/v0.5.1/MagnetometerSystem-v0.5.1-setup.exe artifacts/v0.5.1/SHA256SUMS.txt
```

`--verify-tag` 用于避免发布工具在错误提交上隐式创建标签。Release 页面已存在时先核对标签和附件，不盲目覆盖现有产物。

**Gitee 是单独的后续操作。** 只有明确获准后才按 [CONTRIBUTING.md](../CONTRIBUTING.md) 同步已合入 GitHub `master` 的提交，并另外核对、推送标签及创建 Gitee Release。PR 尚未合并时，不借发布流程把功能分支推到 Gitee 主分支。经授权发布到 Gitee 时，使用与 GitHub 相同的已验证包、完整文件名和 `SHA256SUMS.txt`。

## 第 6 步：验证附件与用户更新路径

GitHub 发布后至少检查：

1. 标签指向记录的源提交，Release 页面可访问，三个附件名称与大小正确。
2. 下载附件并按 `SHA256SUMS.txt` 重新校验；不能只验证上传前的本地副本。
3. 分别检查便携包、安装包的程序版本、构建提交和 `portable.marker` 行为；确认不带 `-dirty`。记录实际启动/安装检查结果，不把打包成功当作运行验收。
4. 把来源 PR、SHA、校验结果和未验证项写入发布记录。未授权 Gitee 同步时，明确用户需从 GitHub 手动下载。

验证应用更新链路时，分别选择自动、GitHub 和 Gitee，确认发现的版本、平台、发行说明、下载进度和 SHA256。两边同版本产物必须字节一致，自动模式只将同版本发布作为镜像；不能让缺失附件的新版本被另一平台的旧包替代。已发布的 V0.5.0 客户端另需验证 Gitee 旧入口。安装版应在保存成功后启动安装器并重启，便携版应打开下载目录。保存失败必须阻止安装，不能丢弃尾批后退出。

可独立检查 Gitee 元数据，但接口返回成功不能代替客户端验证：

```powershell
Invoke-RestMethod https://gitee.com/api/v5/repos/yialu/MagnetometerSystem/releases/latest
Invoke-RestMethod https://api.github.com/repos/YIALU/MagnetometerSystem/releases/latest -Headers @{'User-Agent'='MagnetometerSystem'}
```

公开仓库的更新查询使用匿名 API；不要把发布凭据或个人 token 写进客户端或源码。

## 更新机制说明

- 启动后延迟 8 秒静默检查，两次静默检查至少间隔 24 小时；网络失败不记录成功检查时间，避免长期压制重试。
- 「系统设置 → 软件更新」可关闭自动检查并指定平台；「关于」中的手动检查不受 24 小时间隔限制。用户可跳过某个版本；两平台的预发布及草稿均不向普通用户提示。自动模式有平台查询失败时保留诊断，不记为两边均成功检查。
- 下载目录为 `%LOCALAPPDATA%\MagnetometerSystem\updates`。先写 `.part` 临时文件，校验通过才改为正式文件；失败清理临时文件。
- 必须先取得所选完整文件名对应的有效 SHA256。清单缺失、无法下载或没有该包的有效校验值时，拒绝应用内下载和缓存复用；缓存也必须校验后才能使用。超过 7 天的旧下载会清理。
- 网络下载失败时仅尝试同版本镜像，各自读取 SHA256 清单并从头下载。校验失败或取消不切换。最终失败时显示重试和当前所选平台的发行版页面入口。
- SQLite 位于 `%LOCALAPPDATA%\MagnetometerSystem`，与程序目录分离。升级前仍应备份；覆盖安装保留数据库，卸载询问是否删除数据且默认为否。旧固定列数据迁移状态见 README。

## 常见问题

**工作区不干净**：检查 `git status --short`，保留并单独处理已有工作，或使用干净 worktree。不要为了打包而随意删除文件、扩大忽略规则或使用 `-AllowDirty`；临时试打包不能上传为正式版本。

**找不到 ISCC.exe**：安装带所需简体中文语言文件的兼容编译器（推荐 Inno Setup 7），或在明确只发布便携版时使用 `-Mode Portable`。脚本在编译前检查安装器工具。

**HEAD 没有精确标签或版本不一致**：核对已审查提交、`Directory.Build.props` 和 annotated `v0.5.1`。标签若指向其他提交，不要用强制改标签来掩盖来源差异，按提交、审查、标签步骤处理。

**用户收不到更新提示**：检查所选平台是否有正式 Release、三段版本号、自动检查开关和跳过版本设置。已发布的 V0.5.0 只查询 Gitee，只有 GitHub Release 时不会收到提示。能看到版本但不能下载时，检查完整附件名与有效 SHA256 清单。

**安装器中文乱码**：`build.ps1` 和 `installer/MagnetometerSystem.iss` 需要保留 UTF-8 BOM，供 Windows PowerShell 5.1 正确读取中文；不要在编辑发布说明时顺带转换这些脚本的编码。
